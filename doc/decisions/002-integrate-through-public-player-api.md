# 仅通过现有玩家公共 API 接入游戏

本项目基于 [ra2web](https://github.com/ra2web/ra2web.github.io) 设计独立的本机语音指挥伴随程序。

## 背景

游戏仓库提供发布文件、公共接口声明和示例。项目开发者不是游戏维护者，伴随程序需要独立编写、开源和维护，不能要求修改游戏实现或补充上游接口。

控制对象是对局页面内的 `window.werhd`。类型声明描述该对象，无法作为 Node.js 中直接控制游戏的 SDK；游戏也没有本地 HTTP 控制入口。

## 决策

ra2commander 独立构建和运行，仅通过固定浏览器桥访问现有公共 API。游戏仓库作为接口、示例和兼容测试参考，不作为 npm 依赖，不导入发布包内部类，也不复制游戏资源。

首版由伴随程序管理专用游戏窗口。游戏适配器维护公开类型与动作映射，记录参考来源和 Git 版本；会话代次、任务归属和效果观察由本机程序补充。

## 备选方案与取舍

| 方案 | 优点 | 未采用或采用的理由 |
| --- | --- | --- |
| 修改游戏实现，新增控制和观测接口 | 可直接获得更完整的状态与控制能力 | 不符合开发者权限和独立项目范围 |
| 直接访问发布包的内部对象 | 可能取得公共接口未开放的信息 | 与现有公共 API 边界冲突，并增加版本耦合 |
| 独立程序与固定公共 API 桥 | 构建、代码和发布独立，可按版本验证兼容 | 采用；承担公共接口的状态与控制缺口 |

## 影响

全部观察与下令仍发生在游戏浏览器页面。本机负责语音、云模型与脚本执行，页面桥只采集有限公开状态和提交动作；单一 tick 入口必须保持短小。

公共 API 没有稳定对局 ID、统一执行回执、路径查询或禁止追击开关。系统通过本地会话标记和后续状态观察处理这些缺口，不能把订单入队当作动作完成。

类型约定和地图资料在伴随项目维护，参考文件通过固定版本链接引用。升级游戏版本后重新验证兼容，项目构建不依赖旁边恰好存在另一份检出目录。

## 验证依据

在实际游戏页面验证快照采集、下令和效果观察；测试离局后旧引用与旧动作失效，回调不因耗时或异常停用。实现检查应确认仅使用公共接口；无法完成的操作反馈限制，不依赖私有对象兜底。

接口事实与固定来源见[API 调查](../architecture/game-api.md)，桥接和会话方案见[架构设计](../architecture/overview.md)。
