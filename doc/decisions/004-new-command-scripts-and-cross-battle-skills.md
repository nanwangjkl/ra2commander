# 每条命令生成新脚本，跨局能力沉淀为 Skill

本项目基于 [ra2web](https://github.com/ra2web/ra2web.github.io) 设计独立的本机语音指挥伴随程序。

## 背景

任务应能对应到玩家的某条命令，明确知道它控制哪些单位、接受了哪些条件。直接改旧脚本参数或保留跨局任务实例，容易混淆命令归属、取消效果和状态生命周期。

每次完全重写已有通用操作又会增加生成成本和行为差异。玩家希望有效操作能够跨局复用，同时坚持每条命令拥有独立的新 JS。

## 决策

每条玩家命令生成新 JS 和任务实例，绑定当前对局、对象、目标和授权。代码修复建立该命令的新代码版本，不产生新战略许可。

通用操作提炼为带版本的游戏 Skill，经验证和开发者确认后入库。命令脚本可以组合 Skill；共享的是代码，单位 ID、执行进度、局部状态和权限按任务隔离，不能跨局继承。

## 备选方案与取舍

| 方案 | 优点 | 未采用或采用的理由 |
| --- | --- | --- |
| 复用同一长期任务，只修改参数 | 生成和启动成本较低 | 不符合每命令新脚本要求，命令与状态归属容易混淆 |
| 每次从零生成全部操作 | 单条命令自包含 | 已验证能力无法稳定复用，生成成本和差异增大 |
| 新脚本调用版本化 Skill | 任务独立，通用代码可验证后复用 | 采用；需要版本记录、审核和状态隔离 |

## 影响

记录命令、代码版本和 Skill 版本，效果可追溯。候选 Skill 不自动进入运行库；开发者检查适用范围、接口要求、样本和限制后确认。

普通改令在新脚本准备完成后切换；停止或禁止类先撤权，本次新脚本仍须建立。迟到的旧云回答和动作不能重新激活被取消任务，跨局状态不能影响新局。

Skill 仍受调用命令约束，不能自行创建目标、抽调其他编队或扩大追击、撤退和生产权限。代码复用并不等于任务授权复用。

## 验证依据

同样口令在不同对局中产生不同任务和状态，既有 Skill 可以共用。切换、取消、修复和离局后，检查旧版本动作失效；未入库候选不能加载，Skill 内部动作仍接受原命令授权检查。

生命周期与 Skill 结构见[架构设计](../architecture/overview.md)，入库验证见[实施与验证计划](../roadmap/implementation-plan.md)。
