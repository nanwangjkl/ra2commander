## 目标与边界

本轮降低新增能力的改动成本、命令等待时间和重复存储量。保留以下机制：

- 全局与每个编队分别接受改令，全部编队平级；单位归属唯一，交接事实独立保存。
- 目标、生产提交与执行进度独立于脚本记忆，重编和恢复不重播已完成动作。
- Markdown 维护能力、规则说明、战术与 Skill；实际游戏规则优先读取公开 API。
- 停止、取消与新版本使旧动作失效；QuickJS 隔离和提交前的对局、归属、额度复查继续存在。
- 保留当前玩家命令和侧栏反馈体验，不追加录音、其他地图、寄生状态识别等功能。

阶段 1～4 保持现有目标语义与模型生成职责。阶段 5 才调整固定流程的执行方式，并同步补充 ADR 006 的职责边界；本计划不把该调整描述成已经采用的架构。

## 阶段 1：让各控制对象公平获得执行机会

当前固定顺序逐队执行，新快照到来会从头重新开始。两队离线模拟出现 `A、A、A、A、B`；编译干跑与实战还共用一个串行执行器。

实施：

1. 运行时记录轮转位置，新快照更新数据时不重置调度顺序；为每轮设置执行预算，避免某个控制对象长期占用。
2. 编译检查和实时运行分别使用独立的 `StepExecutor`，保持现有隔离方式。编译检查等待或异常不占用实战执行队列。
3. 继续丢弃失效结果，停止与取消保持直接处理；不通过放宽对局、归属检查换取响应。
4. 仅记录验证所需的轮次、等待时间和首个动作时间，不添加游戏内提示、自动截图或额外侧栏面板。

主要范围：`packages/runtime/src/index.ts`、`packages/js-worker/src/index.ts`、`apps/companion/src/main.ts`、`controller.ts`。

验收：

- 持续更新快照的受控模拟中，每个仍可执行的控制对象都能在有限轮次获得机会；一个脚本超时后其他对象继续运行。
- 编译检查执行期间，已有部队仍能提交有效动作；停止后迟到候选和动作不生效。
- 用户实机同时运行探路、生产和至少两个作战编队，观察改令期间的响应。

回退：调度和执行器接线单独提交，可恢复原调度；目标和运行时文件格式不变。

## 阶段 4：减少归档重复，整理文档

最近一局 5 条命令的归档约 16.3 MiB，其中观察约 13.7 MiB；每条完整转写保存约 9～10 次。这是本轮比较基线，不设脱离实际内容的固定大小门槛。

实施：

1. 提示词、脚本和 Skill 正文按内容哈希在对局目录内保存一次，事件通过引用关联；仍能还原每次实际请求、响应与生效版本。
2. 日常记录变化与阶段进度，错误、用户反馈和结束等关键时点保留完整观察；控制写入批次和内存占用。
3. 命令转写与对局归档使用同一写入来源，卡片恢复读取当前局记录；旧 `.runtime/transcripts/` 保留兼容读入。
4. 执行状态仍从运行时检查点按同局条件恢复，归档不进入任务重放路径。反馈持久化成功后才返回保存成功。
5. 旧归档保持可读，不批量覆盖历史文件。新记录格式有版本，异常中断后能处理尾部残缺或孤立内容文件。
6. 更新架构总览的现状说明；将 AGENTS 中重复的功能细节移至对应规范，环境、运行命令、约束和文档入口仍留在 AGENTS。历史设计继续保留在路线图和 ADR 中。

主要范围：`battle-records.ts`、`transcript.ts`、`command-log.ts`、相关记录契约、README、AGENTS、架构与归档规范。

验收：

- 用相同输入和观察序列比较大小、重复内容次数与写入耗时，同时确认原话、理解、模型请求、代码、成果和反馈都能还原。
- 验证反馈保存失败的提示、进程重启、末行损坏和旧归档读取；完整内容不因去重丢失。
- 用户实际提交反馈并关闭对局后，能从本机记录准确复盘；不新增历史管理或代码预览 UI。

回退：新旧读取兼容，写入格式独立提交；必要时恢复旧写入方式，已有新记录继续由兼容读取器访问。

## 阶段 5：固定动作直接由本机执行

这是行为架构调整，前四阶段验收后再实施。模型仍解释玩家命令、决定需要表达的行动要求；固定步骤由已有宿主逻辑推进，战术判断继续使用模型生成脚本。

### 5A：建筑操作试点

1. 建筑维修和出售使用已有目标处理器产生动作，直接进入统一提交路径，省去模型生成转发代码。
2. 全局与各编队仍是控制对象。同一控制对象统一调度、暂停、取消、进度和动作预算；每个目标只有一个动作来源。
3. 向生成脚本提供其负责的目标，过滤旧脚本对已迁移目标的残留动作；混合任务也不能重复提交。原生目标的增改不触发无关脚本重编。
4. 执行方式写入目标的明确标识，并提供旧状态默认值；只有实际生成/替换代码才增加脚本版本，侧栏对固定流程显示“本机执行”。
5. 固定实现的异常反馈给开发记录，不进入让云模型重写固定实现的循环；战术脚本保留原有有限修复机制。
