# 里程碑后的架构整理

用户于 2026-10-30 批准按架构回看建议实施。先交付保持现有行为的职责整理，用户验收后再单独推进固定脚本本机化；不由本计划启动真实语音、历史对战或设置功能。

## 第一轮：职责与执行事实收拢

本轮实施范围：

1. `TaskRuntime` 保留对局生命周期、调度、目标激活、归属交接及统一动作提交。将 Skill 准备/取消/完成衔接、掩护与碾压协调、生产预留/撤销及落点冲突分别收回 `skill-lifecycle.ts`、`combat-actions.ts`、`production-submission.ts`。静态依赖注入，不引入插件注册或通用流程引擎。
2. 普通攻击、守卫、移动和碾压共用 `unit-orders.ts` 的订单与集火状态。`coverMotion` 只保存掩护的预测、重聚、追赶等进度。成功回执统一更新去重事实和临时出口让路恢复索引；实际产物、投弹、碾压配对仍由各自事实判断。
3. 恢复旧 v3/v4 检查点时，将原 `coverMotion.orders/focusTargetId` 转为 `facts.unitOrders`，保留暂停、进度、目标与生产台账，不改变调用方传入的旧数据。新写入仍为 v4；历史复盘原档不改写。
4. `CommandIntent` 一次提取分句、编队、地域、兵种提及及明确的敌方选择。组织、部署、基地防守和作战校正共用该事实；地域、空地和移动/攻击合并统一在作战校正中处理。绑定修正沿用同一分句识别规则，继续保留原话、模型原始结果及修正记录。
5. 更新架构现状，不迁移生产、探路、维修车的脚本执行方式，也不改变模型、游戏 Skill 参数或 UI。

验证使用现有命令链路、并发取消、生产与集结、掩护、碾压和同局恢复测试。只补充旧订单兼容、失败回执重试和多分句相互独立的代表检查。实机验收由用户进行，不自动截图、录屏、发测试命令或生成实机报告。

当前状态：用户于 2026-10-30 复测胜局后验收本轮及掩护、生产关联和方位识别修正，要求先提交推送，再开始下一阶段。

## 后续：固定流程本机化

第一轮验收后单独安排：先迁移探路的动态落点发令和维修车的组装/维修发令，再评估生产协调。生产须保留共享前置、队列空间、补电、出厂交接、预留与未知回执、取消及同局恢复。

下一阶段已获用户授权，先迁移探路的动态落点发令；新造侦察犬仍沿用现有生产执行方式，现有犬直接接入本机探索。逐区60%覆盖、并行分工、受阻重试、战损、暂停／取消及同局恢复保持现有规则。此类迁移交付后等待用户验收，再开始维修车；不同时迁移生产协调。

探路实现为 `scout@1.4.0`：复用原落点与覆盖算法，按成功回执去重，现有犬无需代码生成，新造犬只生成生产代码。无标记旧探索保持脚本执行，并提供 `RA2C_SCOUT_EXECUTOR=script` 回退。用户已于 2026-10-30 实机验收并要求提交推送。

用户随后批准继续维修车本机化。本轮 `repair-vehicle@1.1.0` 迁移现有组件编队、工程师上车、逐车维修与待命跟随发令，沿用原配对和伤员分配算法，保留出厂集结、交接、战损及暂停／取消／恢复。新造整套只生成全局生产代码，已有组件和直接维修不生成代码。旧无标记维修保持脚本，提供 `RA2C_REPAIR_EXECUTOR=script` 回退。该轮已由用户验收并提交 `578d395`；组件生产随后按下述生产计划迁移。

每类迁移单独比较模型调用和理解后首个有效动作，用户验收后再继续。游戏 Skill 仍使用 Markdown 定义，保留生成脚本和 QuickJS 的现有用途。

生产协调的[两阶段方案](production-native-execution.md)已获用户批准，用户于 2026-10-31 明确授权继续阶段2。有限生产、持续补电及显式队列控制均已接通本机，共享规则准备、供需、额度和提交事实，已于 2026-10-31 通过用户实机验收并获准提交推送。队列归属沿用原表，未决意图随同局恢复；旧脚本及按能力回退保留。

## 页面桥：共享纯算法
