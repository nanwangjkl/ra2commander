# 阶段 1 开发方案：最近十局与模型设置

状态：2026-11-01 用户明确历史页只需最近 10 局及单局完整 ZIP 下载，设置页需编辑模型 URL 和 Key，并要求评估本地数据库。用户随后批准开始；1A 与 1B 已实现，2026-11-02 完成相关开发检查并获用户验收、要求提交推送；用户同日授权开始阶段 2 语音识别，客户端另行安排。

本方案细化[后续开发阶段](client-development-phases.md)的阶段 1，取代此前关于本阶段独立复盘页面、历史反馈编辑及通用设置项的建议。已完成的归档、当前局反馈和游戏执行保持原样。

## 数据库评估

建议本轮不接入 SQLite，继续使用现有文件归档，并新增小型模型配置文件。

| 需求 | 现有基础及建议 |
| --- | --- |
| 最近 10 局列表 | `BattleRecords.list()` 已读取 `meta.json` 并按开局时间倒序排列；列表不需要展开对局事件 |
| 单局完整调试包 | 已有 JSONL 事件、哈希正文与无损导出校验；新增 ZIP 容器即可，不需要先把事件迁入数据库 |
| URL、Key、模型名 | 少量配置，用带版本的 JSON 文件、串行保存和临时文件原子替换即可 |
| 后续客户端 | 页面通过宿主接口读写配置；存储位置可随客户端适配，不必为打包先迁移归档 |

SQLite 适用于本地应用，官方也列出应用文件格式、数据分析和本地存储等用途，见 [SQLite 适用场景](https://www.sqlite.org/whentouse.html)。本项目已有可用归档格式，本轮查询仅为最近十局及少量配置；新增数据库会带来迁移、模式维护和双份事实一致性工作，当前收益有限。这是结合本项目需求的取舍，不是 SQLite 的能力限制。

以后若需要跨局全文检索、复杂条件筛选、统计聚合或元数据扫描出现实际瓶颈，再考虑以 SQLite 保存可重建的查询索引；现有事件及正文仍可保留为复盘原档。本轮不引入 ORM 或通用存储框架。

## 1A：历史页与 ZIP 下载

历史页只做列表和下载：

- 按开局时间倒序显示最近 10 个历史对局，展示时间、已确认胜负或“未记录”、命令数和反馈数，每局提供“下载调试包”。
- “显示十局”不等于“只保存十局”，不自动删除更早的归档。未进入游戏的失败命令不算一局；当前仍进行中的对局保留在指挥记录，不占历史十局名额。胜负缺失时不猜结果。
- 列表从宿主读取轻量元数据，关闭游戏后仍可用；切页不重载 iframe、不丢输入或反馈草稿，不额外调用模型。

ZIP 内建议保留以下自包含结构：

```text
<battle-id>/
  manifest.json       导出格式、对局标识、校验信息及实际已采集的版本信息
  meta.json           对局索引
  summary.md          复用已有派生摘要，正文引用仍可访问
  events.jsonl        完整事件序列
  objects/            事件引用的全部正文
```

“完整”覆盖该局已保存的命令原话、理解与绑定、模型请求和响应、提示词版本、各版脚本及修复、动作回执、战场观察、错误与历次反馈。早期记录未采集的内容无法补回，清单说明缺失情况；导出工具当前版本与对局采集版本分开标明。

实现约束：

- 复用现有临时紧凑副本及逐事件内容哈希校验，所有原始逻辑事件均保留；原档不改写。ZIP 直接压缩 JSONL 和正文文件，避免先 gzip 再套 ZIP，也不额外加入展开后重复的整局 `record.json`。
- 不打包 `.env`、本机模型配置、认证请求头、浏览器 profile、全局恢复状态、其他对局或游戏素材。API Key 不进入配置诊断和版本信息。
- 使用跨平台 ZIP 实现。紧凑转换、校验和压缩放入独立 worker，避免现有同步转换在 HTTP 处理期间阻塞采样、命令理解和发令；按流处理，不把整局或 ZIP 全部装入页面内存。
- 同一局重复点击合并正在进行的导出；前端显示准备及失败原因，文件校验通过后才提供最终下载，失败和断连清理临时文件。源记录导出期间变化时明确提示重试，不交付混杂版本的包。
- 扩展离线读取工具支持 ZIP，例如 `pnpm records:read <zip路径> --summary`；保留现有 `.ra2c.jsonl.gz` 导出和读取兼容。开发者无需游戏、原始归档目录或数据库即可 inspect，包内代码只作为资料读取。

本轮不增加独立复盘浏览页、历史命令反馈编辑、搜索统计、自动上传或旧档清理。

## 1B：模型 URL 与 Key 设置

用户于 2026-11-02 明确收窄为 URL、Key、模型名称三个字段及保存、测试连接按钮：支持不同模型，但只保留当前一套配置。移除服务选择、配置名称、来源、清除 Key 和重新加载控件。

- 仅以 `.runtime/settings.json` 版本 2 保存当前一套 `{baseUrl,model,apiKey}` 及修订号，每次保存覆盖旧配置，不维护模型列表或默认服务选择。
- 没有本机配置时兼容已有环境配置，按原默认顺序取第一套可用值；不改写 `.env`，不复制其他环境模型。旧版本 1 文件只保留当时选中的一套并原子转换，其余配置项移除。
- URL、Key 和模型名成组校验；更换 URL 需要输入适用的 Key，未改 URL 时空 Key 保留当前值。Key 不回显、不进入设置响应、日志或导出包。
- 保存使用临时文件、原子替换和落盘同步，成功后才替换新请求使用的 provider 实例；在途请求继续原实例，失败保留旧配置与表单输入。
- URL 仅接受 HTTP(S) Base URL，兼容客户端补接 `/chat/completions`。模型名沿用请求的必填字段，没有固定模型候选名单。
- 切换页签读取当前配置并保留草稿；并发更新后过时保存报错，可重新切换页签读取。保存不发送模型请求；只有主动点击测试连接才用当前表单发起最小模型请求，不保存或切换当前配置。

本轮不增加其他设置项；后续客户端阶段再适配平台凭据存储和用户数据目录。具体行为见[模型设置规范](../spec/model-settings.md)。

## 实施与验收

按 1A、1B 两步开发，作为新阶段 1 统一交付；用户验收后才安排语音阶段。当前实现保留游戏与任务生命周期，交付时仅重连 Companion，不刷新进行中的游戏。

主要改动为历史/设置页组件、`WorkbenchApi`、`BattleRecords` 的历史筛选、ZIP worker 与离线读取、宿主模型配置存储和 provider 选择入口。不迁移现有归档、不改战术或目标调度算法。

验收与必要检查：

1. 归档超过十局时只显示最近十局，不删除其他记录；未进局失败记录和正在进行的当前局按上述规则处理，未记录胜负保持未知。
2. 下载 ZIP 在另一目录中可离线读取，事件、正文、错误、代码和反馈完整；用有代表性的旧 v1/v2 与新 v3 记录验证逻辑内容一致，不复制模型配置或 Key。
3. 较大记录在后台导出时，现有命令和游戏采样继续推进；重复点击、源文件变化、缺失正文、下载失败与临时文件清理有明确行为。
4. 未配置 `.env` 时可从页面配置并使用模型；已有环境配置仍可读取，覆盖保存和重启后生效，旧多配置只迁移当前一套，空 Key 不误删旧值，失败不破坏旧配置。
5. 模型请求在途时保存新配置，不打断旧请求，不恢复已取消任务；设置保存不请求模型或下发游戏动作，连接测试不保存配置或切换当前模型，Key 不出现在设置响应、日志或调试包中。
6. 使用已有类型、命令链路、归档导出和 UI 检查，新增用例只针对上述接线与具体故障。实机由用户观看，不自动截图、录屏或生成额外测试报告。

已实现行为与接口见[模型设置](../spec/model-settings.md)和[对局记录](../spec/battle-records.md)。ZIP 使用跨平台 `yazl`/`yauzl` 按流读写，单次大记录转换在独立 worker 中完成；浏览器下载不缓冲完整 ZIP，临时文件随下载结束、失败、退出或过期清理。
