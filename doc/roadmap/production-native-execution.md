# 生产协调本机化计划

状态：用户已于 2026-10-30 批准实施，基线 `578d395`，并于 2026-10-31 明确要求继续阶段2。有限生产、持续补电与显式队列控制均已接通本机实现，用户已于 2026-10-31 实机验收通过并要求提交推送。两阶段完成，不自动进入其他路线图。已实现行为见[生产执行方式](../spec/production-execution.md)。

本计划承接[里程碑后的架构整理](architecture-consolidation.md)。目标是让普通生产不再等待模型生成转发代码，保留玩家命令、真实游戏规则与已有生产进度。

## 现状与判断

科技前置、剩余产量、队列空位、真实产物、建筑放置、出厂集结和生产撤销已经有本机实现。模型生成的全局脚本主要按这些事实提出生产、放置及编队动作。这部分适合迁到现有静态目标处理器，不需要另一套生产系统。

代码中的两个迁移前提必须先解决：

- `prepare-goals.ts` 目前通过脚本编译调用，负责真实科技树、生产设施、目标类型、队列类型和耗电。标记为本机目标后不能跳过这些准备。
- 持续补电的待建耗电目前按本次准备的目标汇总。固定生产迁出编译后，仍走脚本的补电目标也必须看到新增本机建筑的耗电，不能依靠重编无关脚本更新事实。

固定生产从第一阶段就要与其他生产目标共用前置、队列和台账。探路、维修车、掩护的组件生产均通过同一入口迁移，不在每个 Skill 内重复实现。

## 共同约束

- 模型继续理解玩家要造什么、造多少、编入哪队及位置要求；名称、参数、规则说明和 Skill 保留在 Markdown。科技树以当前对局公开规则为准。
- 固定数量表示本次新增总量。已有同名单位或建筑不能抵消目标，战损不减少累计产出，也不自行补造。现有 `reinforce` 是已有成员转编，不改为自动生产补兵。
- 复用 `ProductionRecord`、`productionProgress` 和统一提交。发送前仍保存预留；回执未知、出生归属不明时保留事实，不重置计数重发。
- 同名目标沿用现有串行确认；共享前置跨本机与旧脚本复用。同一帧的队列空位共用，就绪建筑去重；某项目缺钱、队列满、集结点受阻或无合法落点时，其他可执行目标继续。
- 继续逐次入队前复查集结点、静态障碍与建筑占地冲突。坦克和步兵到达出生时的集结点并完成停车交接后才开放后续控制，矿车保留原生采矿。
- 保留建筑逐座方位、异形分区、间距与搬迁完成依赖；无合法落点时保留就绪建筑，不能换到别处或额外补造。
- 暂停、停止、改量、取消、对局结束与同局恢复沿用原语义。明确取消生产目标才撤销其剩余队列；Skill 取消和全局停止继续只停后续调度。
- 控制对象、共享动作预算与全局故障暂停语义不变，不增加通用流程引擎、经济规划器或另一份生产账本。

## 阶段 1：固定数量生产

范围为普通有限生产，以及探路、维修车、掩护 Skill 的有限生产目标。持续补电和带显式队列暂停参数的目标暂沿用脚本；两种执行方式须正常共存。

实施：

1. 将目标准备与代码生成解耦。复用同一个 `prepareGoals`，让新本机生产在激活前拿到真实前置、类型和队列信息；每次命令固定提示词及游戏目录版本，同次准备复用规则查询。规则查询不占普通绑定队列，也不拖住其他控制对象的本机激活。准备结果写回前复查对局、目标版本及取消状态，迟到结果不恢复旧任务。
2. 准备等待或失败只影响对应目标，其他已生效目标继续。修改现有目标时保留已提交数量、产物与交接状态；准备就绪后再切换生效要求。原脚本准备路径继续复用相同函数。
3. 在 `goals/production.ts` 提出固定动作：放置已就绪建筑、交接可用产物、提交当前可造且仍有额度的项目。使用已有 `productionPlan`、约束和提交台账，不重算另一套科技树或维护脚本式完成标记。
4. 本机与脚本共用队列裁剪、共享前置归账、同名串行、建筑放置及生产预留。维护“候选动作不等于已提交”的规则；队列未公开时沿用当前规则，不能因数组为空而永远不生产，也不能据此重复入队。
5. 将跨目标的待建耗电事实从“本次编译的目标集合”改为基于当前已准备生产目标和实际提交动态计算，覆盖新本机目标及已有脚本目标，避免迁移期间补电漏算；补电发令本身仍在阶段 2 迁移。
6. 生产执行方式在公共目标准备边界统一确定，覆盖自然语言、直接能力、终端和各 Skill 的内部目标。侧栏沿用“本机执行”和现有进度，不因新增本机生产重编无关脚本或增加代码版本。
7. 增加 `RA2C_PRODUCTION_EXECUTOR=script` 回退，默认只影响本轮支持的新目标。无标记旧目标继续脚本；显式回退已有本机目标时保留原 ID、台账、产物及准备事实，等待脚本接管，不重放生产。同步本阶段的生产能力、战术、运行说明和 ADR 006 执行边界，保留旧脚本说明供回退。

主要改动位置：`prepare-goals.ts`、`controller.ts`、公共能力执行入口、`execution-modes.ts`、`goals/production.ts`，以及统一生产事实的计算入口。`production-submission.ts`、集结点和交接逻辑以复用为主，仅为确认的接线缺口调整。

验收：

- 已展开基地、尚未补齐生产前置时，下达“制造战车工厂”，按本局实际规则补前置并放置，已有同名建筑不抵消明确新增目标。
- “制造5辆坦克并编入1队”只生产本次5辆；出厂到点前不停车编队，第一名交接完成即可执行后续任务，其他成员继续到点交接。
- 同时进行固定生产、探路和两辆维修车生产时，共享前置不重复，IFV与工程师独立推进；已有补电脚本能够看到本机待建建筑的耗电。
- 指定分区／方位、建筑间距、基地搬迁后建造、集结点被占和队列满时保持现有行为，不影响其他可执行项目。
- 调高或调低目标数量不重置累计提交。调低只收紧后续下单，已入队数量不因此自动撤销；明确取消时按现有规则撤剩余队列。
- 暂停、取消、准备途中改令／换局、未决回执重启和新旧目标共存时不重复生产、不丢失产物、不由迟到结果恢复任务。
- 仅含本轮支持的本机能力时，语音入口保留一次目标理解、零代码生成；直接能力零模型请求。新造狗和新造维修车的生产分支也省去原全局代码生成。包含其他脚本能力的混合命令仍按实际需要生成代码。

阶段1已完成离线检查，用户随后明确要求开始阶段2，按此授权继续。

## 阶段 2：持续补电与显式队列控制

在阶段 1 的共享事实及提交链路上扩展，不另建调度系统：

1. 将 `production.power` 的持续发令接入本机。沿用现有真实电量、待建耗电和已提交电厂计算，满足余量后待命，耗电再增或电厂损失后继续补足。
2. 多个补电目标和明确新造电厂的目标共用提交事实，处理本机、旧脚本和不同规则版本目标并存，避免同一缺口重复补电。玩家明确要求新增的电厂数量仍须保留。
3. 迁移带显式队列控制参数的有限生产。只处理玩家明确允许、且当前可观察的队列；只恢复本目标实际暂停的队列，保留同局事实，不能干预玩家或其他目标暂停的队列。
4. 沿用当前目标收到顺序和同名确认规则；受阻目标让出本轮机会。持续补电不阻止其他可执行目标，也不隐含改变其他建筑或单位的生产优先级。
5. 同步生产能力、战术说明和架构现状，保留脚本回退所需正文及编译检查，不删除 QuickJS 或其他仍在使用的脚本能力。

已实现：持续补电按所有已提交建筑的待建耗电与供电统一计算，优先使用提交来源捕获的规则；同名电厂提交可归账到明确新增目标，不吞数量。显式队列控制避开本目标仍需要的前置和产物队列，产出已确认后即开始恢复，不等待出厂交接；完成状态须等恢复确认。暂停、恢复先保存意图，正回执和真实队列状态分开确认；取消期间迟到的暂停正回执也继续收尾。未知回执保留，同局重启及脚本回退不盲目重发，也不认领玩家已暂停的队列。

验收：

- “制造间谍卫星，保持电量健康”按实际科技树建造、预估待建耗电并补电；电量健康后不继续追加，新增耗电后恢复补足。
- 两次补电命令、明确新增电厂、多个建筑和不同生产队列并行时不重复计算同一缺口，不吞掉明确新增数量，不阻塞其余项目。
- 显式队列暂停／恢复、重复取消、暂停期间重启、回执未知及本机转脚本回退时保留原有边界与进度。
- 本机生产和补电不再请求代码生成或代码修复；固定实现错误进入现有错误反馈，供开发修正，缺钱和队列等待按正常 pending 表达。

## 验证与交付

优先复用现有生产、科技树、放置、集结、取消、并发和恢复测试，只补准备脱离编译、混合来源共享额度／耗电、迟到准备失效及完整本机生产链路等关键缺口，不为每个兵种单写测试。

涉及绑定和提示正文时，先生成能力类型，再运行类型、测试、提示词与能力检查；目录和地图不变时不重复导入素材。模型调用次数用隔离替身核对，实际响应从已有命令／动作事件确认，不把离线耗时当成云模型延迟。

实机由用户观看和验收。交付时重启 Companion、保留浏览器和对局；不自动下测试命令、截图、录屏或生成额外测试报告。验收后按用户要求提交，不由本计划启动真实语音或页签内容开发。

两阶段完成后复核生产的剩余脚本用途，再决定本轮整理是否收尾；页面桥与 UI 生命周期整理保持独立。
