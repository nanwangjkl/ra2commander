## 共同行为与技术约定

### 界面

- 工作台新增独立路径，如 `/commander/`；游戏 iframe 继续加载原来的游戏路径，沿用当前 origin、资源地址和浏览器 profile。
- 右侧栏占独立空间，支持调整宽度与折叠。侧栏滚动和内容更新不抢镜头、不遮挡地图、不重建游戏 iframe。
- 命令以卡片显示时间、来源、原话、理解摘要、实际选择、当前状态及错误。详细错误按需展开，常态不展示源码、堆栈或模型内部数据。
- 保留文本输入，前期用于模拟语音转写和调试；真实语音接入后走同一条命令链路。
- 按“快速反应、允许误判、后续纠错”的原则执行。显示理解结果不增加确认步骤，也不等待玩家阅读后才行动。

### 通信与记录

- 浏览器以 HTTP 提交命令，Node 返回命令 ID 后在后台推进处理；以 SSE 推送理解、生成和执行状态，不等待整条命令结束才更新界面。
- 命令 ID 在接收输入时建立，早于规则查询和模型调用；语音阶段进一步提前到录音开始。网络失败、识别失败、模型返回非法内容也有对应卡片。
- 卡片区分“命令正在处理”和“任务正在执行”。一条命令产生多个目标时展示各目标结果，不能因某一项成功就把整条命令标为全部完成。
- 用命令 ID、目标 ID、控制对象及脚本版本关联后续反馈。全局脚本可能包含多条命令，无法定位的错误标为全局错误，不随意归到最后一句命令。
- 从结构化事件生成界面，不解析终端输出，不轮询完整运行时 JSON，不向浏览器推送每帧战场数据。
- 侧栏记录独立保存，复用现有转写记录和运行状态中的事实；不再建立另一套互相冲突的目标状态。初版用轻量文件和内存记录，不引入数据库或通用事件平台。
- 侧栏历史用于显示，不自动把整段历史附加到模型提示词。侧栏显示不额外调用模型。
- 事件重连只补齐显示状态，不重放命令；主动重复发送命令仍表示一条新指令。

### 游戏与进程

- 游戏桥明确绑定游戏 frame，识别快照来源，避免把工作台或其他页面当成游戏。
- Companion 重启或侧栏重连不自动刷新、跳转或重新创建游戏 iframe。首次切换工作台安排在新对局开始前，避免为了迁移界面中断正在进行的对局。
- 全屏针对整个工作台，游戏单独全屏的入口需要协调，避免右侧栏消失。
- 刷新承载游戏的整个页面仍会重载游戏，不承诺通过 iframe 保住这种情况下的对局。历史恢复验收通过连接重建或 Companion 重启完成，不依赖刷新整页。
- 麦克风采集归工作台；语音识别归独立进程或本地服务；模型与 QuickJS 维持现有执行路径。
- 当前以 macOS 开发环境验收；界面和通信不写死平台，Windows 的安装与音频适配单独安排后续验收。

## 阶段 1：工作台与游戏接入

目的：先确认游戏在 iframe 中能够正常运行和接受现有命令，再扩展界面功能。

开发内容：

1. 由现有 HTTPS 服务提供工作台与静态界面，形成左游戏、右侧栏骨架的布局。前端采用轻量 HTML、CSS、TypeScript 与最小静态构建。
2. 支持侧栏折叠、调整宽度和整个工作台全屏，协调游戏的尺寸与全屏入口。
3. 将 `WerhdBridge` 的规则查询、状态读取、动作提交、快照来源和旧桥重装适配到游戏 frame；调整启动对话框处理与游戏页定位。
4. 沿用现有资源与 profile；保留已有终端、TCP 指挥入口用于验证。
5. 侧栏显示游戏连接状态即可，本阶段不接真实命令卡片或麦克风。

用户验收：

- 打开工作台，游戏资源、音效和开局正常，右侧有独立侧栏。
- 调整侧栏和窗口尺寸、进入与退出全屏后，游戏画面正常，巡视、鼠标指向和地图滚动无明显错位。
- 在新对局通过现有命令入口执行“展开基地”，实际展开成功，证明桥接不止能读状态。
- Companion 重启后可重新连接同一对局，游戏不被自动刷新，也不重复发出展开命令。

交付后等待阶段 1 用户验收。若 iframe 暴露资源、输入或引擎兼容问题，在本阶段解决或提交方案调整，不带问题进入下一阶段。

2026-10-23 交付说明：工作台入口为 `/commander/`，右侧目前只显示连接状态与空记录区域；终端/TCP 命令沿用。隔离浏览器检查了侧栏折叠、拖动、尺寸、全屏转交及 frame 复用；实际对局通过模拟语音展开为盟军建造厂。实机发现生成请求使用 `selfSample` 而运行时使用 `self`，导致展开脚本空转，已统一编译上下文与运行时字段后重试成功。同日用户确认验收通过，并授权提交后进入阶段 2。

## 阶段 2：命令侧栏与生成过程反馈

目的：在游戏右侧实时看到输入、理解和命令准备过程中的错误。

开发内容：

1. 引入命令记录与结构化事件，统一接入界面文本、终端 `say` 与 TCP `say`，保留原有入口。
2. 增加命令提交与事件订阅接口；侧栏提交后立即建立卡片，显示“已收到”“理解中”“生成脚本”“已生效/执行中”等真实阶段。
3. 模型解析完成即显示理解摘要；宿主绑定完成即显示实际选择；不等脚本生成结束才一次性输出所有内容。
4. 展示规则查询、模型网络、JSON 解析、目标绑定与脚本编译错误，以及同一句话部分跳过的情况。被取消、合并或取代的请求按真实原因说明。
5. 新请求到来时界面保持可输入；侧栏不增加串行等待或确认步骤。保持当前命令合并、替换与停止语义。
6. 界面静态更新与游戏 iframe 分开，避免卡片刷新导致游戏重载或焦点被抢占。

用户验收：

- 在侧栏输入“制造战车工厂”，立即出现原话，随后能看到理解、实际选择和脚本是否生效；游戏确实开始执行。
- 从终端或 TCP 发出的模拟语音同样出现在侧栏，不只记录界面输入。
- 在可控故障样例中看到模型连接或生成错误；保留原话和错误，不出现“没有任何反馈”的空白。
- 同句可执行与无法绑定部分分别显示结果，可执行部分仍能推进。
- 连续下令时记录可区分，界面不要求确认理解，不抢走游戏巡视焦点。

“脚本已生效”仅代表代码开始运行。2026-10-24 用户追加要求提前显示执行/完成状态，本次接入下述状态反馈，不以此代替阶段 2 验收或启动阶段 3 的全部范围。

交付后等待阶段 2 用户验收。

2026-10-23 交付说明：侧栏新增命令卡片与文本输入。命令统一经命令记录（`apps/companion/src/command-log.ts`）产生结构化事件：已收到、理解中、理解完成（含摘要）、目标绑定（含实际选择）、部分未执行、生成脚本、已生效/执行中、失败与取消。界面经 `POST /commander/say` 提交并立即获得命令 ID，`GET /commander/events`（SSE）按阶段增量推送；终端与 TCP 的 `say` 同样进入事件流。断线重连按 `Last-Event-ID` 补齐内存内事件，历史恢复仍属阶段 3。无对局或未绑定部分会保留原话与失败原因，不出现空白卡片。

2026-10-24 修订：规则查询、模型请求、取消及零目标均有结束反馈；仅实际提交成功发布脚本生效事件，按目标 ID、控制对象及版本更新各目标，合并版本会继续反馈保留的旧命令。输入可连续提交，异步响应不改变焦点；退出主动清理 SSE。重启时独立更新侧栏模块与样式，不重载游戏。按用户当前单图配置自动绑定冰天雪地分区，新局与重连均生效，保留手动重绑入口。用户尚未验收阶段 2。

2026-10-24 执行状态追加：卡片区分执行中、持续执行、已完成、受阻、暂停与运行出错，多目标逐项显示并汇总完成数，已完成卡片弱化显示。实际产出/基地转换确认完成，编队移动以全部存活成员到达目的地附近确认，持续补电和守区不误报完成；所有目标结束后脚本不再持续空转。状态变化才产生事件。为衔接本次更新，重启时从已有转写文件恢复当前局卡片，不重放命令；完整多局历史、通用修复过程和语音仍按后续阶段推进。

2026-10-24 命令语义修正：现有坦克编队与新造后编队分开，侧栏理解与实际绑定计划同源；指定队伍的区域清敌作为单个目标，按异形边界筛选敌人，行军不扩大选敌范围。普通攻击移除两层射程前置拦截，过期对象仅跳过当次动作；决策见 [008](../decisions/008-command-actions-and-engine-attack.md)。

## 阶段 3：运行错误、任务状态与记录恢复

2026-10-25 用户追加授权跨局记录与逐命令反馈：每张卡片可评价执行情况并备注，按对局保存原话、模型理解、脚本生成和修复版本、实际成果与反馈；游戏关闭后可以查看旧局、补充意见并导出复盘。按[对局记录规范](../spec/battle-records.md)实现，不额外采集画面或请求云模型，等待用户体验验收。本次追加不启动阶段 4，也不以自动检查代替阶段 3 的用户验收。

2026-10-25 用户修订：归档用于玩家与开发 Agent 共同复盘。移除工作台顶部历史对局和导出 UI，以及命令卡片的代码预览，只保留当前局命令与反馈。归档继续写本机文件，目前不另建查看 UI；未来如需要，使用独立页面与 URL。本轮只调整反馈系统，不处理反馈中提及的游戏执行问题。

2026-10-25 验收：用户重新启动 Companion 后确认本次本机归档、逐命令反馈与侧栏精简验收成功。其余阶段边界不变。

目的：命令生效之后发生的问题仍然可见，侧栏断开后能恢复显示而不重复执行。

开发内容：

1. 将任务阻塞、运行异常、暂停、自动修复和修复失败接入侧栏；重复的同类错误合并显示，避免刷屏。
2. 根据运行时已有事实更新任务状态：生产与展开以实际观测确认；持续补电、守区等长期目标保持“持续执行”。没有可靠完成依据时，不凭动作提交或模型描述宣布完成。
3. 处理一条命令多个目标、一个全局脚本多个命令、脚本被后续版本替换等关联；旧命令的有效目标保留反馈，不因换代码丢失追踪。
4. 保存并恢复命令卡片，提供当前状态同步与 SSE 重连。重复事件不生成重复卡片，断线补齐不重新执行历史命令。
5. Companion 重启时，记录按对局区分；旧局保留为历史，不能继续显示为当前局正在执行。重连期间明确显示连接状态。

用户验收：

- 一条命令先显示执行中，实际建筑完成后再显示目标完成；持续补电不会在一次补电后显示整项结束。
- 用可控本地故障样例验证“已生效后发生运行错误”的反馈；能够看到受影响任务及修复结果。故障样例不修改玩家正常任务来制造损失。
- 连续添加两个全局目标后，相关运行错误不会无依据地归到最后一句话；无法定位时明确显示全局错误。
- 断开再恢复侧栏连接或重启 Companion，当前对局保留、卡片恢复、已有生产不重复下单。
- 开始另一对局后，旧局记录可区分，旧任务不会显示为新局执行中的命令。

交付后等待阶段 3 用户验收。至此，用户要求的命令侧栏完成，真实语音仍未接入。

## 阶段 4：真实语音输入

目的：玩家在游戏里按住说话，松开后直接进入已经验收的命令链路。

开发内容：

1. 外层工作台负责麦克风授权、设备选择、输入音量与录音状态；首次显式启用麦克风后，提供可配置的按键说话入口。
2. 处理游戏 frame 与侧栏焦点，避免录音快捷键触发游戏其他操作。忽略按住时的重复按键，正常松开只提交一次；切窗或失焦结束并取消该次录音，不继续悬挂录音。
3. 对接一个常驻本地识别后端，优先验证 `whisper.cpp`。音频转换格式与模型按当前机器实测选定，识别进程在开始指挥前就绪，不为每条命令重新加载模型。
4. 识别通过独立进程/服务运行。第一版按句提交音频；不先引入流式识别、唤醒词、后台全局热键或多种识别引擎。
5. 录音开始建立同一张命令卡片，依次显示录音、识别、原话、理解与执行。最终转写直接提交一次，不增加人工确认；中间识别片段不触发游戏动作。
6. 识别失败、空音频、麦克风权限拒绝和设备断开均有简短反馈；默认不留存录音文件，保留转写和命令处理记录。
7. 沿用阶段 2、3 的记录、错误与任务关联，不为语音单独建立另一套执行流程。文本模拟入口继续可用。

用户验收：

- 先检查麦克风与录音状态；焦点在游戏内也能按住录音、松开提交，侧栏显示识别出的原话。
- 在新对局口述“展开基地”“制造战车工厂”“制造5辆坦克并编入1队”，逐条观察理解和游戏实际动作。无需复制文字到终端，也不额外点确认。
- 其他已有任务运行期间输入新语音，录音和识别不使现有编队或生产整体停下。
- 长按、松开、切窗和恢复焦点后不重复提交，不持续录音、不误触发其他游戏快捷键。
- 空音频、拒绝权限及可控识别失败时能看到具体错误，游戏没有因此收到重复或空命令。
- 在当前机器观察语音结束到转写、理解和首次动作的等待；记录必要时间供调优，先保证快速可用，不预先承诺未经实测的响应秒数。

交付后等待阶段 4 用户验收。增加流式识别、Windows 音频适配或桌面安装包均另行确定范围。

## 预计改动位置

| 位置 | 主要工作 |
| --- | --- |
| `apps/companion/ui/` | 新工作台、侧栏、文本输入、录音界面 |

## 检查与交付约定

- 每阶段运行与改动相关的类型检查和已有测试。只针对新增基本链路或发现的具体故障补少量检查，不建立庞大测试体系。
- 游戏嵌入、布局、键盘焦点与语音实际效果通过实机观察验证，不以模拟测试通过代替用户体验验收。
- 必要的模型/运行故障可在隔离的本地样例中验证，不为验收故意破坏用户进行中的对局。
- 每阶段交付仅提供启动方法、简短变更与检查结果、该阶段验收步骤和已知限制。不生成截图、录像或测试报告。
- 实现时同步更新使用说明；提交和推送遵循用户当时的指令，阶段验收状态只在用户明确反馈后更新。

后续若引入 Electron，主要复用这次的界面、命令事件、语音服务与后端，仅另行适配窗口和游戏接入。它不属于本次四阶段的自动延伸。
