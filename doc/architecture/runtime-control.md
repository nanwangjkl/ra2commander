# 运行时行为与调试入口

本页收录已实现的命令行为、目标完成口径与终端调试约定。架构入口见[架构总览](overview.md)，环境与构建运行见[AGENTS.md](../../AGENTS.md)。

## 命令与执行状态

工作台顶部显示的是 Companion 与游戏对局的连接状态。关闭游戏页面后会清理旧快照并寻找重新打开的游戏 frame；未进入对局显示“等待进入对局”，连接查询失败显示“伴随程序未连接”，不再把读取失败误报成“游戏加载中”。后台恢复后自动重新查询，不刷新游戏。

侧栏按目标区分执行中、持续执行、已完成、受阻、暂停和运行出错；一条命令多个目标全部完成才标为已完成，完成卡片弱化显示。生产按实际观察到的产物、展开按建造厂出现确认完成，移动按部队主体抵达目的地附近确认完成。持续补电与守区不自动标为完成。状态只在改变时推送；事件窗口滚动不丢失同局目标关联，完成后追加产量也继续更新原命令。重启恢复原命令 ID，不重放命令。

每条卡片的“反馈”可选择符合预期／部分达成／不符合预期并填写备注。反馈归档用于玩家与开发 Agent 复盘，Companion 只保留当前局命令及反馈，不提供历史选择、导出或代码预览；目前不建设归档查看页面，未来如需 UI 应使用独立页面与 URL。资料由 Node 直接保存在 `.runtime/battles/<battle-id>/`：`events.jsonl` v2 追加记录变化与哈希引用，`objects/` 保存正文，`meta.json` 为索引，`summary.md` 整理复盘并链接脚本正文。反馈文件同步后才确认成功，关闭游戏不会删除文件；不依赖浏览器存储、数据库或云同步。记录只读，不恢复历史任务；无截图、录屏或额外模型调用。旧转写尽力迁入，无法补回原先丢失的代码与成果。详见[对局记录规范](../spec/battle-records.md)。

模拟语音入口使用 `say <文字>`，将文字作为语音转写结果：先由当前云模型解析目标，再按执行方式启用本机固定流程或生成替换脚本；真实录音与识别尚未接入。支持展开基地、现有单位编队、生产并编队、前往已绑定地名、指定编队的区域清敌、明确要求的持续补电，以及已有作战编队全图进攻。固定模型提示统一放在 `prompts/templates/`，由 `packages/command/src/prompt-loader.ts` 在新命令或编译请求边界加载、校验并计算内容版本；同一条转写命令的理解与各控制对象编译固定使用同一套模板，不在逐 tick 执行中重读。原话、模型原始解析、校正后的操作、目标及实际请求提示版本统一保存在 `.runtime/battles/`；旧 `.runtime/transcripts/` 仅兼容读入。侧栏主要理解摘要来自实际绑定计划。“5个坦克编入1队”操作现有未编队坦克，“所有坦克编入1队”合并现有匹配单位；不足时执行可用部分并反馈，不擅自生产。

## 提示词、能力与游戏目录

提示词维护：`interpret.md` 控制文字理解，`compile.md` 控制全局与编队脚本生成，`repair.md` 和 `validation-feedback.md` 分别接受 `{{error}}`、`{{errors}}`。编辑后执行 `pnpm prompts:check`；模板在下一条新命令或新修复请求生效，同次请求的异步准备、重新绑定及校验重试固定使用原版本。模板出错时打印具体文件错误，当前进程沿用上一套完整可用模板；首次加载无可用版本则明确报错。校验命令始终严格读取磁盘，可附模板目录参数。终端及自动修复在请求时输出提示版本；生效脚本的 `script.promptVersion` 随 v3 状态保存，旧状态缺少该字段仍可恢复。修改提示文件不替换已经运行的脚本。

`binding-repair.md` 控制语音绑定失败后的单次重决策，成功部分先运行，失败部分单独修正。执行时还会本机检查有条件却连续900游戏 tick 无进展的目标，携带近期动作/结果请求限次修复；缺钱、队列忙、未决生产、交接等待和已确认无合法落点不计时。停滞修复期间旧脚本继续，保留生产进度，停止/取消和新命令使迟到结果失效。详见[自动恢复](../spec/automatic-recovery.md)。

30 项玩家能力统一在 `prompts/capabilities/*.md` 声明名称、参数、默认值与说明；`interpret.md` 的 `{{capabilities}}` 由加载器组合该目录。停止、暂停、恢复、转编、解散、守区、补员、集结、目标取消与改总量均可经 `say`/侧栏调用。绑定后的摘要来自共用执行计划；直接控制无需额外生成脚本。`cap list` 查看能力，`cap <能力ID> <JSON参数>` 直接调用，原有玩家 CLI 语法也是同一入口的适配器。开发定义与完整接线表见[玩家基础能力](../spec/player-capabilities.md)。

修改能力正文或参数说明在下一条命令生效。修改参数结构、默认值、ID 或绑定器时，先运行 `pnpm capabilities:generate`，再运行 `pnpm capabilities:check`、`pnpm typecheck` 和相关测试，并重启 Companion；生成文件 `packages/command/src/capability-types.generated.ts` 不手工编辑。新增能力还须实现绑定器。模板、能力、游戏目录、战术和 Skill 共同参与提示版本，类型不一致或重载出错保留上一套完整定义。检查命令可从其他目录启动；指定自定义模板目录时，其同级须有 `capabilities/`。

游戏目录由 `prompts/games/current-mod.md` 选择；当前配置为共和国之辉，完整单位/建筑与中文名称由 `catalogFile` 指向的 `prompts/games/catalogs/ra2web-gonghui.json` 自动导入，Markdown 维护常用角色与别名。未解锁项目也可识别，实际前置、可造性、队列、电力与角色标记以对局 API 为准。战术在 `prompts/tactics/` 按目标选择通用、生产、作战、管理主题，修复/校验重试再加入恢复主题。基础 `compile.md` 只保留脚本契约。目录、战术修改也在下一条命令生效并参与同一提示版本；自定义模板目录使用 `<根>/prompts/templates/`，携带同级 `capabilities/`、`games/`、`tactics/` 以及 `<根>/skills/`。`pnpm prompts:check` 严格检查全部内容，详见[规则与战术规范](../spec/game-rules-and-tactics.md)。

“造飞机”等通用类别由目录中的类型角色统一识别，候选检索与生产绑定共用同一规则。复合命令为每个提及类别保留候选，不因已匹配电厂就遗漏飞机；按可造性、国家限制和阵营选择具体项目，不必逐机添加别名。类型角色允许空 `members` 配合 `match`，新增 MOD 项目按真实类型匹配。

完整目录更新：`pnpm game-data:import [游戏站点目录] [输出JSON] [游戏ID]`，默认读取 `RA2C_GAME_DIR` 或 `~/my/code/ra2web.github.io` 的 `res/overlay/rules.ini`、`ra2.csf`，无需原始资源包或 Python。随后运行 `pnpm game-data:check`、`pnpm prompts:check` 和相关检查。规则和中文文件哈希形成数据版本，已有命令固定其捕获版本。换 MOD 时重新导入并更新 `catalogFile`，不用逐单位维护科技配方。详见[完整游戏目录与通用科技树](../spec/full-game-catalog.md)。

运行时提供生产目标的 `productionPlan`，包含缺失前置、已提交待完成前置、本步可造候选、就绪建筑与未满足条件；模型按这些动态事实执行。引擎确认目标可造时，不再等待历史缺项或额外补造旧前置。名称选择、坦克筛选与前置类别共用当前游戏目录；同次规则准备复用查询，使用命令捕获的目录版本。侦察犬也可通过首个 `scout` Skill 执行探路，见下文。

## Skill 与专项操作

`say 探路` 默认优先使用现有未编队侦察犬（最多三条），没有时才新造并建立独立侦察队；`say 用五条狗探路` 覆盖数量，`say 用已有狗探路` 使用现有成员、不追加生产。首名成员实际停车交接完成即可出发，其余后续加入。按分区内多个落点分散探索，宿主分批读取实际揭开格子，排除原生地形与引擎边界确定的图外格子，每个目标分区的有效范围分别达到至少 60% 才达标，全部目标分区达标后完成；达标区不再分配落点。侧栏显示达标分区数和未达标区的实际覆盖。优先区域中心及中心附近未知有效格子，成员独立并行，原地停滞才换点；覆盖继续增长时恢复尝试额度，收尾对暂缓区额外换点重试一轮。无法继续如实显示部分完成/失败，不无限补狗。`say 取消探路` 停止本次后续步骤；给侦察队改令后旧 Skill 不再接管。Skill 版本和探索进度随 v4 保存，同局重启不重复生产。定义、覆盖口径和开发入口见[探路 Skill](../spec/scouting-skills.md)。

`say 造维修车` / `say 造修理车` 调用第二个 `repair-vehicle` Skill，默认新造一个 IFV 和一名工程师，入队后按实际载员确认组装，再持续维修己方受损坦克。`say 造两辆维修车并编入1队` 新造两套，分头组装、并行修理不同坦克；满血或目标失效后重新分工，无伤员时待命。已有维修队可用 `vehicle.repair` 指定坦克或跟随编队，不重复生产。`selector=repairVehicles` 选择已载工程师的 IFV。Skill 与组装/维修事实同局持久化，取消、转队和改令不重复补造。详见[维修车 Skill](../spec/repair-vehicle-skill.md)。

执行器与宿主共用生产队列调度：多个目标共享本步空位，按脚本动作顺序先推进能放下的数量，其余留到下一步，不因重复使用同一空位而整批暂停；项目、目标额度及实际前置校验继续保留。

`say 5辆坦克组成1队，5个警犬掩护` 使用现有成员；`say 造5辆坦克编入1队，2个IFV掩护1队` 接通有限生产、停车交接与角色分配。`cover@0.2.1` 的移动、巡逻、守区和进攻统一由本机协调：正常行军让最慢成员直达终点，其余按游戏规则速度和公开方向预测跟随，严重脱队才停车；接敌后掩护贴近威胁前侧、就地支援并优先对空。规则速度按每格256内部单位换算，不靠位移测速；速度和武器查询在tick外，最终掩护开火在桥再次确认射程。普通未启用掩护的攻击不增加射程拒绝。`formation.uncover` 解除角色保留队伍和当前任务，停止整队仍用 `control.stop`。用户已批准合并后续阶段，待整体验收。详见[掩护 Skill](../spec/cover-skill.md)。

建筑命令明确指定方位时，`production.produce` 使用可选 `placementDirections`、`placementAnchor`，宿主按游戏画面的八方向选择合法落点，逐座观察真实位置后确认完成。例如“基地上方、左边、下边各造一座巨炮，补三个电厂”，只有巨炮携带方位要求，电厂沿用默认选址。指定方向无地可放时保留就绪建筑并重试，其他可执行目标继续；不会擅自改方向或额外补造。未提方位的命令不生成位置约束。方位和实际落点随 v4 恢复，详见[建筑方位要求](../spec/building-placement.md)。

`building.repair` 直接开启选定受损建筑的原生扳手，无需维修车；缺钱等待、满血完成，重复命令不关闭已开启的维修。`building.sell` 出售当前选定的己方可售建筑，跳过禁售项目并以实际离场确认；不包含车辆或后续新建筑。发令与完成事实随 v4 保存，取消只撤销后续调度。详见[建筑维修与出售](../spec/building-operations.md)。

`base.relocate` 支持建造厂收起、基地车移至分区/坐标并重新展开，不需要作战编队。实际变形后的 ID、阶段与候选落点由宿主持久化；生成前校验移动和重新展开阶段。`production.produce.placementRegion` 指定异形分区内建造，`afterRelocation` 及同区目标关联搬迁完成依赖；搬迁失败或取消时不在旧址继续。详见[基地搬迁与区域建造](../spec/base-relocation.md)。

`economy.gather` 使用现有矿车在指定分区采矿，不区分矿种。宿主分批查询公开矿格，给空闲成员分配真实 gather；忙碌矿车继续由游戏采集、返厂和卸货。没有已知矿格时先进入该区寻找或等待发现，抵达不标记完成。未编队成员使用全局脚本，已编队成员沿用各队脚本；发令事实随 v4 保存，取消与改令撤销后续动作。详见[指定分区采矿](../spec/regional-mining.md)。

现有作战单位可用 `combat.attack` 按选择器或 ID 直接攻击，无需先建队。未编队成员走全局脚本，已编队成员沿用对应队脚本。飞机装弹未满时显示 pending（等待就绪），各机满弹后独立出击；本次实际发射一次即完成，返航及装弹交给游戏，不重复派出或等待目标摧毁。绑定修正保留原单位、编队与攻击范围。详见[现有单位攻击与飞机出击](../spec/selected-attacks-and-sorties.md)。

同名明确建设目标与共享前置的新提交统一归账：其他目标先建出的兵营、重工也计入当时尚未完成的明确建设目标，避免替换脚本后再造一份。建筑 `no-spot/cannot-place` 保留就绪项目并持续重试放置，不取消或重造。旧有建筑和新增目标之前的提交不抵消玩家后来明确追加的数量。

“所有战斗单位”使用共用 `combat` 选择器，按本局武器和角色排除矿车、基地车、工程师及建筑，包含坦克、IFV 等作战成员；`vehicles` 仍包含矿车。同句向同一队的多个选择合并去重，编队与后续移动按原顺序绑定；新队尚在建立/交接时，移动目标等待真实成员就绪，不因暂未注册而跳过。新编队生效后再初始化真实成员基准。后续改令正常替换旧任务时，卡片显示新命令及替换原因。

IFV/FV/多功能步兵车作为目录候选在开局尚未解锁时就可绑定，再按实际规则补齐前置。同句话同队多个移动合并成一个有序路线目标；`combat.move` 的 `patrol=true` 允许途中交战，明确终点的路线走完一次结束，不默认无限循环。“基地附近”按当前己方建造厂或基地车位置绑定。宿主用实际到达推进路点索引并随 v3 状态保存，每步 `spec.destination` 是当前站；换脚本不重置进度，后续整句新命令仍替换该队路线。侧栏区分产量与路点进度。

移动、路线和未编队集结共用 `packages/runtime/src/arrival.ts` 的主体到达判定：按存活受控人数扩大半径（当前为 `max(3, ceil(2.5×√N))` 格），至少 80% 成员进入范围即可继续，少量掉队成员保留归属并继续跟随下一站；无人、仅少数前锋到达或全队交接未完成不算到达。相同 `arrival` 事实传给脚本，避免模型另设全员 1–2 格挤点条件。该判定只表示抵达目的地，不代表区域敌人已经清空。

模型调用按控制对象合并：整句理解通常一次，全局和每个需要变更脚本的编队各生成一次；不同控制对象目前依次编译，执行阶段只运行本机脚本。校验重试、重新绑定及自动修复另计。详细协调方式见[玩家基础能力](../spec/player-capabilities.md)。

当前只使用冰天雪地，进入新对局或 Companion 重连后会自动绑定其默认分区，无需先执行 `map use ice`；该命令保留为手动重绑入口。这是单图默认配置，不通过地图尺寸猜测地图名称。地名移动使用分区内部候选格，是否可达以实际位置确认。区域清敌用真实异形边界筛选敌人；行军可经过其他区域，到达不能当作清空分区。普通攻击不再被宿主或页面桥的射程预判拦截，游戏处理接近和开火。`say 制造间谍卫星，保持电量健康` 会分别建立卫星生产和持续补电目标；未指定电力余量时，本轮测试默认至少留100，已提交电厂在完成前计入待补电量，避免重复下单。补电目标持续到取消。

## 六句实机测试

六句实机测试需要一个只有基地车的新冰天雪地对局：

```sh
pnpm scenario:voice
pnpm scenario:voice --resume  # 同局续测，已完成项目不重放
```

测试定义在 `tests/scenarios/voice-six-commands.json`，按原话依次调用模型；读取实际建造、产出、编队、分区位置、电力与敌方败北状态，在终端反馈进度。补电同时检查过程缺电，最终健康但曾缺电会标记部分达标；已确认败北的玩家可能不再是combatant。执行器仅在 `.runtime/voice-six/progress.json` 保存续测所需的步骤、指令响应和末次败北状态，不采集画面或生成报告；`--resume` 也可读取旧版 `result.json` 迁移进度。本测试访问已配置云模型并会执行真实游戏动作，不属于 `pnpm test`。首次实机结果见[六句测试记录](../roadmap/voice-six-commands.md)。

## 终端调试与控制对象

命令有两个入口，命令集相同（`help` 查看）：

- 终端交互（TTY 前台运行时）：`ra2c>` 提示符直接输入。
- TCP 命令通道（始终可用，供自动化脚本）：`printf 'move all 50 60\n' | nc 127.0.0.1 8790`。

战斗任务须显式提供调试授权参数；生产数量和队列权限也独立于模型保存。例如（单位 ID 用 `units` 查询，坐标须按当前地图选择；建队目标完成后再给该队下令）：

```text
form create 一队 101,102
task new 守区 @一队 --region=40,40,60,60 --retreat=0.6,20,20 守区，战损超过六成回撤
task stop 守区
produce MTNK 5 --pause-queues=2 优先生产
goal list
reinforce @一队 MTNK 6
```

`--mode=hold` 为默认守区模式；`move` 只允许赶路，`assault` 额外允许区内攻击移动。`--retreat=比例,x,y` 只在任务原始成员阵亡比例严格超过阈值后允许回撤，触发后不自动返回。缺省无队列暂停/恢复权限；恢复仅限本任务实际暂停的队列，无法观测状态的队列会反馈限制。`--pause-queues` 编号为 0=建筑、1=防御、2=步兵、3=车辆、4=飞机、5=船。生产前置各授权一次，目标按数量累计，修复和重启不重置额度；不确定提交结果保留额度并报告。任意自然语言条件尚未形成通用授权解析器，当前条件任务支持显式地域和战损阈值；录音识别仍待实现。

每队独立一份脚本，全局一份脚本。`produce`、`form create/transfer/dissolve`、`reinforce` 和 `rally` 都更新全局目标并整体替换其代码；`task new <标签> @编队 ...` 仅替换对应编队代码。`form create` 也支持单位 ID、范围或兵种筛选。编队成员变更停车提交确认后交接，`form list` 查看实际归属。

`goal list` 显示目标状态、待生效变更和生产提交记录；`goal edit <生产目标ID> <总量>` 保留已提交进度；`goal cancel <目标ID>` 立即停止该目标的后续执行，若为生产目标还撤销其尚在游戏队列中的数量，保留已造产物，其余目标继续。撤销以真实队列变化确认，记录与原始提交一同持久化；旧已取消生产目标仍有未决提交时可再次发令。详见[生产取消](../spec/production-cancellation.md)。`global pause/resume` 控制全局脚本及本机目标，`task stop/pause/resume @编队` 控制编队，旧任务标签也可解析到对应编队。普通改令失败时旧目标继续，新增目标显示待生效及失败原因。

`reinforce @编队 <兵种名> <维持数量> [--source=@来源编队]` 持续补员，缺省只使用未编队单位，不额外生产；`rally <ids|all> <x> <y>` 给未编队单位建立集结目标。底层 `move/amove/gather/attack` 仅供调试，涉及活动脚本或待编译命令管理的单位时先停止对应控制对象。

生产提交与实际完成分开记录；`submitted` 表示进入游戏 API 调用，不保证已经成功入队。游戏缺少完整产物出生事件，同名目标按已有提交顺序观察；不会因已造单位阵亡再次下单。不确定或静默未入队的提交先保留额度，人工核对后可用 `goal resolve <提交ID> sent|not-sent` 修正，仅在确认未发送时释放额度。

终端与 TCP 在编译期间仍接收停止命令；`task list` 同时列出全局与编队的脚本版本和编译状态。TCP 按换行分帧，多条并发命令按完成顺序回显。`stop <ids|all>` 会撤销相关编队任务、待编译版本和涉及这些单位的全局管理目标，然后停车。

## 运行恢复

持久化状态写为 v4（保留目标、脚本、生产记录、战损、队列与交接，增加 Skill 和探索事实），兼容读入无 Skill 数据的 v3。v1/v2 不自动合并；首次写新格式前保留旧格式备份。恢复须当前快照确认同局，预留未决记录不自动重放。新版桥在同一游戏 API 上升级时保留对局身份并递增采样序号；换局、刷新或游戏 API 变化仍使旧请求失效，游戏与资源 profile 保留。


新建筑维修、出售、采矿和基地搬迁目标由本机固定流程执行，侧栏显示“本机执行”；语音通常只调用一次理解模型，直接能力调用无模型请求。它们不触发无关脚本重编、不增加代码版本，与脚本共享动作校验、预算和提交。目标执行方式随 v4 保存，无标记旧目标默认 `script`，保持原进度。可分别通过 `RA2C_BUILDING_EXECUTOR`、`RA2C_MINING_EXECUTOR`、`RA2C_RELOCATION_EXECUTOR` 设为 `script` 回退，并保留同一目标与实际进度。详细规则见[建筑操作](../spec/building-operations.md)、[采矿](../spec/regional-mining.md)及[搬迁](../spec/base-relocation.md)。

目标已取消、完成、部分完成或失败后，变形观察停止并冻结旧事实，避免干扰后续生产记账。仅活动目标和回退等待代码接管的已初始化目标继续跟踪真实变形。复合命令的已绑定本机目标先统一启用，再生成各控制对象的脚本；其他对象生成等待或失败不撤销已执行部分。
