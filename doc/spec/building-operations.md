# 建筑维修与出售

最新对局中“维修受损的建筑”和“卖掉所有的建筑”曾因能力目录缺少入口而被跳过。游戏公共 API 已提供 `repair(buildingId)` 和 `sell(objectId)`，现在分别接入 `building.repair` 与 `building.sell`。

两项能力都支持建筑原生 ID、中文名、角色名、明确的 `unitIds` 与数量。只绑定下令时已有的己方匹配建筑，进入全局目标；脚本读取每步 `building.actions`，其他全局目标继续。参数与说明保存在 `prompts/capabilities/building.*.md`，执行说明在 `prompts/tactics/management.md`。

## 维修

“维修受损的建筑”默认选择全部当前受损建筑，直接开启原生扳手维修，无需维修车或工程师，资金消耗由游戏处理。满血后确认完成；缺钱时显示等待就绪，恢复资金后继续；后来新建或再次受损的建筑不自动加入。

原生 `repair()` 是切换开关。页面桥读取实际 `hasWrenchRepair`，只在未开启且仍受损时调用；重复语音、重编和重启都不会把已开启的维修切成关闭。开启后由游戏持续修复，不逐步重发。状态未知时只尝试开启一次，避免盲目切换。目标建筑损失或失去归属时如实显示部分完成或失败，不以消失冒充修复。

## 出售

“卖掉所有的建筑”只选择当前己方可售建筑，不包含车辆、敌方或后续新建建筑。规则明确 `unsellable` 的项目跳过并反馈，其余继续；页面桥提交前再核对实际归属、类型与规则。新出售任务接管所选建筑的旧维修/出售目标，未选择对象的原目标保留。

接口提交不等于完成。宿主记录发令尝试，观察所选建筑实际离场后推进进度；不能据此承诺退款数额，也无法区分售出与同时被敌人摧毁。回执晚于实际离场时保留离场事实，不误记失败。仍存在的建筑有限次重试，持续不生效则报告失败，不无限生成脚本或重新创建目标。

## 恢复与取消

每座建筑的发令、完成与失败事实随 v4 同局保存。替换全局脚本不清零进度，部分建筑离场后仍能重编剩余任务。暂停和取消停止后续发令；游戏已开启的扳手或已提交的出售可继续执行。取消不反向切换维修、不撤销售出，也不追加生产。

离线验证覆盖这两条原话、重复维修、缺钱等待、禁止出售和车辆过滤、实际满血/离场完成、迟到回执、重编、同局恢复与取消。实战效果仍由玩家验收。
