# 指定分区采矿

玩家于 2026-10-26 反馈“所有矿车到一楼的彩色矿区去采矿”被转换成移动到一楼中心，并在抵达后错误显示完成。本能力使用真正的采矿指令，作为持续经济目标执行；当前不区分彩矿和普通矿。

## 入口与对象

`economy.gather` 接受必填 `regionName`，可选 `quantity`（默认 `all`）、`unitIds` 或已有 `formationId`。按照本局规则的 harvester 角色选择现有矿车，不新增生产；不足时使用现有部分并反馈。

“让所有矿车去一楼采矿”对应：

```json
{"capability":"economy.gather","params":{"regionName":"一楼","quantity":"all"}}
```

未编队矿车使用全局脚本；已编队矿车按实际归属分别建立该队的 mining 目标，保持每队一份独立脚本。明确改令后替换所选成员原来的采矿/集结控制，保留其他成员；给矿车小队新命令仍替换该队脚本。

## 矿格观察

通过 `WerhdBridge.readMapBatch` 查询公开 `map.visible/map.tile`，仅对黑幕已揭开的有效格读取 landType。`LandType.Tiberium` 统一视作可采矿格，返回 `ore`；不读取隐藏地图对象、不分析图片、不补游戏 API 或导入矿种数据。

宿主按目标分区真实异形边界生成有界读取批次，每次最多256格。优先复核已分配矿点、矿车附近和区域入口，再继续整个区域的扫描，排除孔洞与边界外格子。尚未发现矿时单次轮询最多4批，发现后限频复查；观察不到不能当作矿石耗尽。仅在该格公开可读且已不再是矿格时移出已知集合。没有已知矿格时先进入目标区寻找或等待发现，不假称采矿完成。

桥的宿主版本与页面版本同时升级，重启可以为已有游戏 frame 补装新桥并保留同局身份。地图观察只更新本机事实，不向游戏发动作，也不调用模型。

## 执行与状态

目标保存选中 ID、区域及入区目的地。`GoalFacts.mining` 保存扫描游标、已知矿点、逐车目标和上次发令事实；`g.mining.actions` 是本步允许发送的具体命令。生成脚本逐项输出这些 request，宿主校验成员、矿点分配和每车单次发令。

首次将矿车指向区内公开矿格，实际调用 `werhd.gather([id], x, y)`，多车尽量分配不同矿点。缺少矿格且尚未进入该区时可先 move；到达后继续找矿，不把移动作为完成。矿车采集、返厂和卸货交给游戏；忙碌时不重新发令。空闲稳定一段时间后才重试或换到其他已知矿格，减少错误落点和闲置。区域限定每次下达的采矿目标；通行路线、返厂和引擎后续寻矿仍遵循游戏自身逻辑。

侧栏显示持续执行、已下达采矿指令的车辆数量，以及矿格搜索/等待情况。接口成功不等于确认正在采集，更不等于完成；当前没有货量和矿种字段，不凭静止位置、抵达或收入推断成果。目标持续到玩家取消、停止或改令；矿车损失/交接后不额外生产。

生成期额外检查“有矿时实际 gather”和“忙碌时无重复发令”，失败反馈模型重新生成。运行时停滞诊断仅针对本步存在可执行命令却没有提交的情况，不对正常采集和卸货报警。

## 取消与恢复

扫描、矿点和发令事实随 v4 目标持久化，旧状态无这些可选字段时继续兼容。重编不清空发令事实；同局恢复不会向仍然忙碌的矿车重复 gather。停止/取消会停车，换局、取消或暂停后迟到的观察被丢弃。底层 `gather <ids|all> <x> <y>` 仍是指定矿格的调试入口，区域采矿应使用本能力。

离线检查覆盖最新反馈命令、并行采矿、返厂/卸货不打断、空闲后换点、独立编队、停止、重编、重连和迟到观察。实机由玩家验收，不自动下测试指令、截图或移动镜头。
