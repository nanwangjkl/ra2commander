# 对局记录与命令反馈

2026-10-25 用户要求：复杂功能测试不能依赖游戏持续打开；每条命令可以快速反馈，将原话、理解、代码、成果与用户意见保存在一起，供后续优化参考。

用途限定为玩家与开发 Agent 共同复盘和优化，不作为面向普通玩家的历史管理功能。

## 使用方式

侧栏每条命令有“反馈”按钮，展开后选择“符合预期／部分达成／不符合预期”，可补充实际问题和期望行为，点击“保存反馈”。备注最多 4000 字。执行状态更新不会清除正在编辑的反馈，也不会抢走输入焦点。重复反馈保留历史，卡片展示最近一次已保存意见。

Companion 侧栏只显示当前局命令、理解、执行状态、错误和逐命令反馈。顶部不提供历史对局选择、导出入口，卡片不提供代码预览。归档由开发者直接读取本地文件；目前不建设归档查看 UI。将来确有需要时，使用独立页面与 URL，不放进游戏工作台。

全部资料保存在本机 `.runtime/battles/<battle-id>/`，已由 `.runtime/` 的 ignore 规则排除出 Git：

| 文件 | 内容 |
| --- | --- |
| `events.jsonl` | v2 追加事件：命令阶段、转写字段变化、编译引用、观察变化与历次反馈 |
| `objects/` | 按 SHA-256 保存的提示词、代码、Skill 与静态规格正文 |
| `meta.json` | 对局标识、时间与命令/反馈数量 |
| `summary.md` | 无需运行游戏即可阅读的复盘，按命令整理解释、状态、错误和用户意见，并链接脚本正文与最后观察到的生产、编队事实 |

由 Companion 的 Node 进程直接写本机文件，不依赖浏览器存储或数据库，也没有云同步。事件先进入当轮写入批次，事件循环让出或达到批次上限后合并追加；命令结束也会刷新事件批次。反馈成功前先同步引用正文，再同步事件文件及目录（`fsync`），然后才确认保存。Markdown 由已保存事实直接整理，不调用云模型；平时按 2 秒窗口合并更新摘要及索引，反馈提交后立即尝试更新，使用临时文件加重命名替换。程序异常退出留下不完整末行时，后续写入先保留 `.incomplete` 备份再修复末尾；中间损坏明确报错，不静默丢弃整个记录。

## 记录与关联

- 侧栏文本与终端/TCP `say` 共用命令 ID。重启恢复保留原 ID，不能把同一条命令变成另一条记录。
- 原话、模型输入消息、模型原始响应、模型名称/用量/耗时、提示版本、原始解析、宿主归一化操作、绑定目标与实际摘要分别保存。解析失败也保留已收到的原始响应。
- 每次脚本生成有独立生成 ID，记录控制对象、完整目标 ID 集合、触发命令（如有）、是否自动修复，以及每次请求/响应、候选代码、校验错误和最终生效版本。全局脚本可以对应多条命令，不把共享脚本的故障强归给最后一句话。直接控制命令可以没有新代码。
- 沿用宿主已有快照，日常有变化的观察至少间隔 60 游戏 tick 合并记录；目标/脚本状态改变、错误、反馈、换局与退出保留完整观察。上下文仍含资金、电力、生产队列、单位与可见敌人。不会周期采集画面，也不保存每一帧或每一个重复移动动作。
- 反馈同时保存当时已观察到的命令/目标状态。之后目标完成，不能反过来修改当时的意见；反馈也不会把系统状态改成“完成”。
- 整条命令状态与侧栏共用事件归并逻辑：全部目标完成才汇总为已完成，仍有目标执行则继续显示执行中；归档按追加顺序处理，兼容 Companion 重启后事件序号重新计数。派生 summary.md 可从原始事件重新生成，不修改 events.jsonl。
- 成果以游戏实际观察为准，生产提交不等于产出，脚本生效不等于目标完成。游戏关闭、刷新或换局后不推断胜负或剩余目标是否完成。

新命令只通过 `CommandLog` 写入同一对局归档，不再另写转写文件；重启卡片从同局归档恢复；无运行目标恢复的中断命令明确显示已中断，不重新解释或执行。旧 `.runtime/transcripts/` 在启动时尽可能迁入历史，并注明由旧记录导入。旧记录未保存的候选代码、过程状态和实际成果无法补回；完整采集从启用本功能后的命令开始。

## v2 存储与兼容读取

每条新日志带 `schemaVersion: 2`。转写按 `requestId` 保存变化字段和删除字段；日常观察保存顶层变化及前序观察序号，关键观察保存完整字段。读取时按顺序合并，返回完整的转写与观察结构。旧 v1 行可以继续读取，同局追加的新行使用 v2，不改写旧行；`meta.json`/`summary.md` 是可重建的索引和复盘资料。

正文引用形如 `{"$ra2cArchive":{"hash":"<sha256>","format":"text"}}`。文本文件位于 `objects/<hash>.txt`，结构化内容位于 `.json`；哈希包含内容类型。编译响应的代码围栏可引用同一份代码正文并保留原前后缀，紧凑 JSON 消息仅在能逐字重建时拆出内部引用。读取返回原消息字符串，不向调用方暴露存储标记；原始数据恰好使用保留标记时进行字面值转义。

静态正文和规格去重，动态单位/队列/进度留在变化事件中，避免每次观察产生碎文件。磁盘摘要使用脚本正文链接，不再次内嵌同一代码；开发接口下载摘要时按需内嵌，便于独立阅读。只有显式读取完整记录时才展开提示词与全部历史观察。写入缓存只保留最新观察，完整历史在明确读取时重建；记录缓存保留当前及近期对局，正文缓存按字节限制；索引列表只读取元数据。

反馈不会在保存失败时返回成功，重试仍走同步路径。崩溃留下的无引用正文不进入事件流、不自动删除；缺失、内容哈希不符、循环引用或中间坏行会明确报错。最后一条缺少换行但完整的记录可继续追加；损坏末行保留 `.incomplete` 备份后截回最后完整位置。归档检查和卡片恢复都不执行游戏动作。

无需开启游戏或 Companion 即可读取：

```sh
pnpm records:read --list
pnpm records:read <battle-id>
pnpm records:read <battle-id> --summary
```

完整 JSON 输出已展开全部引用，便于玩家和开发 Agent 复盘。工具只读现有归档，不恢复运行任务；旧转写的导入由 Companion 启动流程处理。

## 边界与接口

对局归档与运行恢复的 `.runtime/state.json` 分离，读取资料不恢复任务、不调用游戏动作。界面/归档故障不应中断命令执行；存储错误在日志和侧栏连接状态中提示，反馈失败保留输入供重试。关闭游戏或重启 Companion 不删除这些文件。

侧栏仅调用 `GET /commander/commands` 读取当前局的命令事件和已存反馈，不包含历史索引、提示词、编译代码或战场观察点；`POST /commander/feedback` 接受对局 ID、命令 ID、评分与备注。

现有开发用只读接口继续保留：`GET /commander/records` 返回索引，`GET /commander/records/<id>` 返回完整资料，后接 `/summary.md` 或 `/record.json` 下载。它们不再有侧栏入口，也没有归档浏览页面。记录/反馈接口不依赖游戏就绪；接口读取需 Companion 本地 HTTP 服务运行，磁盘摘要可随时直接阅读。

本次不接录音、不做模型自动评分，不依据反馈自动改写提示词或代码；后续由开发者结合上下文修正实现。
