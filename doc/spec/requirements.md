# 产品需求

本项目基于 [ra2web](https://github.com/ra2web/ra2web.github.io) 设计独立的本机语音指挥伴随程序。

状态：已确认。更新日期：2026-10-22。本文件定义首版行为；技术实现见[架构设计](../architecture/overview.md)，决策理由见[ADR](../decisions/README.md)。

## 产品目标

玩家通过语音下达战略命令，并保留对作战目标、去留和生产方向的决定权。AI 编写具体目标选择、火力分配、站位、队形、局部避让和行动时机；玩家无需枚举敌方单位，也不直接操作己方单位。

首版平台、地图、交互方式和验证规模统一记录在[首版范围与实施计划](../roadmap/implementation-plan.md)。

玩家的战略水平影响胜负，因此击败 bot 不作为系统通过条件。首版使用现有公共 API，不修改游戏代码，也不依赖新增上游接口；不连接已经打开的浏览器。

## 快速反应与纠错

RTS 的执行体验优先于命令解释的完全准确。只要存在合理的行动解释，Agent 就应结合当前战况选择并推进，接受误选、误判和次优执行。玩家可以通过后续命令改变要求；为排除所有歧义而下令后不动，是更严重的体验失败。

- “造重工”不要求玩家补充盟军或苏军：先看当前可生产项目，再参考本局阵营和已有设施；仍有多个候选就选一个。
- 选敌、站位、路径与执行顺序不等待最优解，先完成有用动作，再随战况调整。
- 简短反馈实际选择，不把摘要变成确认步骤。一句话中部分目标受阻时，其余可执行部分先行。
- 确实没有相关对象、能力未接入或游戏接口失败时，立即说明具体阻塞；不能把未行动表示为已完成。已有任务在新指令准备期间继续运行，停止与取消立即处理。

验收优先观察首个有效动作的等待时间与有目标却不行动的情况，再评价理解准确性和执行效果。本原则修订此前默认“有歧义先澄清”的规则，见 [ADR 007](../decisions/007-action-first-command-interpretation.md)。

## 指挥权限

AI 只能在玩家任务内选择执行细节。撤退、追击、调队救援、补员和新增生产目标，须有明确命令或命令中的授权条件。

| 玩家要求或场景 | 允许的行为 | 权限边界 |
| --- | --- | --- |
| “守桥” | 在指定守区持续防守，安排区内站位与交火 | 不因战损自行撤退，不离开守区出击 |
| 区外可见敌人在射程内 | 守区内原地射击 | 不为此移出守区或追击 |
| “去东区” | 赶路、必要的地形绕行、避让和集结 | 不为主动接敌改道或停留 |
| “一路打过去” | 沿途停留清敌 | 目标撤离不产生追击许可 |
| “战损超过六成就回撤修理” | 条件满足后去已绑定维修地点 | 条件未满足前不回撤；修完不默认返回原阵地 |
| 缺电、矿车损失或兵力不足 | 显示影响与阻塞原因 | 不擅自补电厂、矿车或部队 |

只有可见战况可用于实时判断。地名和公开静态地图知识不提供隐藏敌军、真实敌方出生位置或未观察到的当前状态。

## 编队与地点

编队通过兵种、位置、角色和名称等语音描述建立，例如“把所有犀牛坦克编成一队”。系统结合当前编队和战况选择合理匹配并显示选择，不因有多个候选等待语音澄清，也不要求玩家选中单位或枚举 ID。

每个单位只归属一个执行编队。没有明确命令不吸纳新造单位，也不自动补充空闲单位；明确转编时才移出旧队。重复队名、成员重叠和来源冲突结合现有归属作合理解释并反馈选择，交接后仍保持单一归属。持续补员必须有明确来源、兵种和条件，生产命令本身不包含补员许可。

战损按任务生效时原始编队成员的阵亡比例计算，受伤不计，补员不重置。阵亡成员仍保留在计算基准中，部署或形态转换不应被直接计为阵亡。

冰天雪地由项目预置大区和桥口等固定小区，并支持语音别名。守桥绑定指定桥口小区，区内可调整站位。分区须以实际地图校准；“这里”“屏幕上这批”不作为首版对象绑定的必要能力。

## 生产与优先级

制造目标包含完成该目标所需的必要前置建设。“尽快出重工”授权真正必需的前置建筑；“尽快”不额外授权经济扩张或产能优化。

| 场景 | 授权结果 |
| --- | --- |
| 指定目标需要电厂或其他硬前置 | 允许完成必要前置，按实际 MOD 规则验证 |
| 已有前置满足，仅因低电力想再补电厂提速 | 不允许 |
| 矿车损失后自动补造 | 不允许，除非已有对应生产命令 |
| 为提速增加第二座重工 | 不允许，除非玩家授权 |

默认沿用游戏原生资金与生产队列机制，不由 AI 分配预算。明确优先级后，可以调整未提交请求的顺序和暂停竞争类别队列；不自动取消已投入资金的项目，无法对已入队同类项目插队时反馈限制。

全局脚本统一协调生产、建设、建队、转编和明确要求的持续补员，编队脚本只指挥本队行动。成员交接先使旧归属结果失效，停车提交得到确认后再开放接收队控制；新成员沿用接收队任务，未安排任务时待命。生产和各编队任务并行运行。电力、资源、建设位置或未授权目标导致阻塞时报告原因，不自行改变生产方向。

## 命令、修复与 Skill

每个编队独立运行一份脚本，全局管理运行一份脚本，两者使用同一套整体替换机制。命令新增、修改或取消任务目标；新增全局目标保留其他目标。普通改令在新脚本准备完成后切换，准备期间旧脚本处理已有有效目标；停止或取消立即阻止相关后续动作，不等待云端生成。新脚本准备失败时报告，已有目标继续。目标、成员归属和生产执行事实独立保存，换代码或修复不重置进度。

编队脚本故障只暂停该编队并尝试停止其单位；全局脚本故障暂停生产与管理的后续动作，已有编队继续，游戏已接收的生产不自动停止。允许自动修复代码并恢复原任务，修复保持原目标与原授权；连续失败达到重试限额后等待处理。云端不可用时，已经运行的本机任务继续执行。

跨局通用操作可以沉淀为 Skill，经开发者验证和确认后入库。新命令生成对应编队或全局的新脚本版本；Skill 不继承其他对局的单位、进度或授权，也不能自行创建战略目标。

玩家只巡视和语音指挥。界面可显示任务摘要、阶段、阻塞和结果，不提供部队手动接管或操作按钮。

## 引擎偏移与示例

首版接受监控并纠正游戏原生攻击造成的短暂追击偏移，记录偏移距离与纠正时间。脚本主动越权仍属错误；引擎偏移不扩大战略授权。具体可接受门槛在实测后确定。

假设一队最初有 10 辆坦克，桥口与维修厂已唯一绑定，玩家说“一队守桥，战损超过六成就撤回维修厂修理”：

1. 脚本在守区内安排选敌、火力与站位，不自动补员或追击。
2. 阵亡 6 辆时恰好为 60%，不满足“超过”；阵亡 7 辆后才触发回撤。
3. 维修厂不存在、不可用或路径受阻时报告，不追加建设目标。
4. 修理结束后保持待命并反馈；返回守桥需要原命令或后续命令授权。
